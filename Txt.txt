Tu es un développeur backend senior spécialisé en Java/Spring Boot.

Je veux ajouter à mon SaaS de facturation un système complet de modèles de factures personnalisables.

## OBJECTIF

Le backend doit permettre à chaque utilisateur/entreprise/tenant de :

* créer plusieurs modèles de facture ;
* modifier un modèle ;
* dupliquer un modèle ;
* supprimer un modèle ;
* définir un modèle par défaut ;
* enregistrer la configuration visuelle du modèle en JSON ;
* versionner les modèles ;
* utiliser un modèle précis lors de la génération d'une facture ;
* générer un rendu HTML/PDF à partir d'un template + des données d'une facture.

## ÉTAPE 1 — ANALYSER LE PROJET

Avant de modifier le code :

1. Analyse l'architecture backend existante.
2. Identifie la version de Java et Spring Boot.
3. Identifie la structure des packages.
4. Identifie les entités User, Company, Tenant, Customer, Invoice et InvoiceItem existantes.
5. Identifie le système d'authentification/autorisation.
6. Identifie le système actuel de génération PDF.
7. Identifie les repositories, services, controllers et DTO existants.
8. Identifie les migrations de base de données utilisées.
9. Réutilise les abstractions existantes.
10. Ne casse aucune fonctionnalité existante.

Adapte toute l'implémentation aux conventions déjà présentes dans le projet.

# 5. SÉCURITÉ

IMPORTANT.

Un utilisateur/tenant ne doit jamais pouvoir :

* consulter un template appartenant à quelqu'un d'autre ;
* modifier un template appartenant à quelqu'un d'autre ;
* supprimer un template appartenant à quelqu'un d'autre ;
* utiliser des données d'un autre tenant.

Respecter le système d'autorisation existant.

---

# 6. TEMPLATE PAR DÉFAUT

Un seul template peut être le template par défaut pour une entreprise/tenant.

Lorsqu'un template devient default :

* désactiver l'ancien default ;
* définir le nouveau default.

Utiliser une transaction pour garantir la cohérence.

---

# 7. VERSIONING

Lorsqu'un template est modifié :

Ne pas écraser l'ancienne version si cela rend impossible le rendu des anciennes factures.

Créer :

V1
V2
V3

Une facture déjà générée doit conserver la référence/version utilisée.

Prévoir une structure permettant de retrouver exactement le template utilisé pour une ancienne facture.

# 10. FACTUR-X / EN 16931

Ne mélange pas le design du template avec les données structurées de la facture.

Le template concerne uniquement la présentation.

L'architecture doit rester compatible avec une future génération :

Facture
→ données structurées EN 16931
→ XML Factur-X
→ PDF visuel

Le template ne doit jamais modifier les données comptables.
